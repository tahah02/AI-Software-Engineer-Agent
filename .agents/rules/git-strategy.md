# Antigravity Rule: Git Strategy, Branching, and Isolation

## Purpose
This rule governs Git operations, repository initialization, branching workflows, Git worktrees, commit conventions, and release manifests across the AAISE platform and the projects it generates.

---

## 1. Dual-Repository Model per Project
Every software project generated by AAISE maintains two independent local Git repositories:
1. `mock-vendor-api/`: Owned and operated solely by **Agent 2**.
2. `channel-app/`: Owned and operated solely by **Agent 3**.

Cross-repository writes are strictly forbidden. The orchestrator bridges interactions between the two services via HTTP/REST contracts and release manifests.

---

## 2. Branching Convention: Modified GitFlow
Both repositories enforce the following branch structure:

```
main (Production Releases - Protected, human approval only)
  ^
  | [Promote via Release Manifest]
release/vX.Y.Z (Pre-release candidate - QA & Security Verified)
  ^
  | [Merge integration]
develop (Active Integration Branch)
  ^
  +-- feature/<feature-name>  (Agent 2 or Agent 3 working branch)
  +-- fix/<defect-id>         (Remediation branch assigned by Agent 1)
  +-- security/<finding-id>   (Vulnerability fix branch)
```

### Branch Rules:
1. **Direct pushes to `main` are strictly prohibited**.
2. Feature branches must branch off `develop` and merge back into `develop` through automated validation.
3. Fix and security branches branch from `develop`, resolve specific findings, and require re-testing before merging.
4. `release/*` branches run the combined suite (Agent 4 black-box test + Agent 5 security scan) before promotion to `main`.

---

## 3. Git Worktrees for Concurrency
When parallel agent tasks run (e.g., Agent 2 implementing mock endpoints while Agent 3 implements channel services), operations MUST take place in isolated **Git Worktrees**:
- Worktree path: `<project_root>/.worktrees/<agent_name>_<task_id>`
- Prevents index locking and working directory corruption.
- Cleanly pruned upon task completion or merge.

---

## 4. Commit Message Standard
All commits generated by agents or developers must adhere to the Conventional Commits specification:
```
<type>(<scope>): <short summary>

[Optional detailed body explaining rationale]

Refs: #<task_or_defect_id>
```
Supported Types: `feat`, `fix`, `test`, `sec`, `docs`, `refactor`, `chore`.

---

## 5. Release Manifest & Compatibility Tracking
Because the platform manages two independent repositories for each project, every release must record a paired manifest in the database:
- Manifest table: `GitReleaseManifests`
- Records: `project_id`, `release_tag`, `channel_commit_hash`, `mock_commit_hash`, `test_run_id`, `security_scan_id`, `approved_by`.
