# Git & Branching Strategy — AAISE

## 1. Overview
Every software engineering project generated by AAISE maintains two separate local Git repositories:
1. `mock-vendor-api`: Dedicated to mock third-party/vendor endpoints (Agent 2).
2. `channel-app`: Dedicated to the main channel service and business logic (Agent 3).

The dual-repository architecture guarantees strict separation between what is deployed as production application code and what is used strictly as a development dependency.

---

## 2. Modified GitFlow Branching Model

```
                    [main] <---------------------------+ (Release Promotion after Human Approval)
                      ^                                |
                      | (Fast-Forward Merge)           |
               [release/vX.Y.Z]                        |
                      ^                                |
                      | (Integration Candidate)        |
                  [develop]                            |
                  ^   ^   ^                            |
                  |   |   |                            |
    +-------------+   |   +-------------+              |
    |                 |                 |              |
[feature/*]       [fix/*]       [security/*]           |
 (New Features)  (QA Bugs)    (Vulnerabilities)        |
```

### 2.1 Branch Definitions & Policies
- **`main`**:
  - The production release branch.
  - **Direct writes/commits by agents are strictly forbidden**.
  - Merges into `main` require all QA tests to pass, zero critical security findings, and explicit human approval via the Release Promotion Gate.
- **`develop`**:
  - The day-to-day integration branch.
  - Receives completed and developer-tested feature and fix branches.
- **`feature/<name>`**:
  - Created off `develop` by Agent 2 or Agent 3 for specific tasks.
  - Merged into `develop` only after local developer unit tests pass in Docker.
- **`fix/<defect-id>`**:
  - Created off `develop` to address specific black-box QA defect specifications dispatched by Agent 1.
- **`security/<finding-id>`**:
  - Created off `develop` to address specific SAST/OWASP findings dispatched by Agent 1.
- **`release/<version>`**:
  - Cut from `develop` when all implementation tasks are complete.
  - Serves as the candidate branch against which Agent 4 runs full black-box QA and Agent 5 runs the complete security audit.

## 3. Git Worktrees for Agent Concurrency

When Agent 2 and Agent 3 develop concurrently, operations occur in isolated **Git Worktrees** to prevent workspace contamination or lock contention:

- **Worktree Paths**:
  - `mock-vendor-api/.worktrees/agent2_task_<id>/`
  - `channel-app/.worktrees/agent3_task_<id>/`
- **Worktree Lifecycle**:
  1. Orchestrator provisions worktree linked to a new `feature/*` branch.
  2. Agent performs edits and unit tests inside the worktree directory.
  3. Agent commits verified changes.
  4. Orchestrator integrates branch to `develop` and prunes the worktree (`git worktree remove --force`).

---

## 4. Conventional Commit Standards
All agent and platform commits must use the Conventional Commits specification:
```
<type>(<scope>): <subject>

[optional body]

Refs: #<task_or_defect_id>
```
- **Allowed Types**:
  - `feat`: A new API endpoint, model, or service.
  - `fix`: Remediation for an Agent 4 QA defect or runtime bug.
  - `sec`: Remediation for an Agent 5 security finding.
  - `test`: Addition or modification of unit/integration test cases.
  - `docs`: Technical documentation or specification updates.
  - `chore`: Dependency updates, build configurations, or formatting.

---

## 5. Release Manifests & Compatibility Pairing
Because two independent repositories exist for each project, releases are tracked via paired commit hashes in `GitReleaseManifests`:
- When a release candidate passes all quality gates, the orchestrator records:
  - `release_tag`: e.g., `v1.0.0`
  - `channel_commit_hash`: `40-character SHA1` of `channel-app`
  - `mock_commit_hash`: `40-character SHA1` of `mock-vendor-api`
  - `test_run_id`: UUID of passing QA test run
  - `security_scan_id`: UUID of clean security scan
- This guarantees full auditability and enables rollback of both components to an exact compatible pair.
